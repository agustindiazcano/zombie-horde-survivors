# Plan: interiors, urban maps, doors and gates, and an engine for several games

Status: **plan only, nothing built.** Written 2026-10-19 from the user's requests: building interiors, urban maps with enterable buildings and streets, test props for these ideas, doors (when they open, bigger gates, sci-fi doors like Half-Life or Alien), and the long-term idea of making a **game engine for several games** and experimenting with it. Build mode ([PLAN-build-mode.md](PLAN-build-mode.md)) already has the first doors and walls; this plan extends it.

## 1. Where the code stands

| Piece   | Today                                                                                                                                                | What it means for this plan                                                          |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| World   | A flat 2D sim on axis-aligned boxes (`Obstacle`), a height map for terrain, surfaces and roads painted in the editor, one floor                      | Interiors fit as many thin boxes; **upper floors need a new idea** (section 3)       |
| Doors   | `structures.types.door` (build mode): a box that is removed from the obstacle list when open; enemies attack it when closed; soldiers pass when open | The seed of every door type below; it has no animation, no lock, no power            |
| Pathing | A flow field on 1 m cells, with a break cost for structures; soldiers walk straight and slide on boxes                                               | Streets and rooms need soldiers to path too (section 6)                              |
| Sight   | `canSee` over the same cell grid; hunters use cones                                                                                                  | Windows and glass need "blocks movement but not sight"; smoke and walls the opposite |
| Render  | Obstacles as brown boxes, structures as coloured boxes                                                                                               | A prop and building kit is needed (CC0 / CC-BY, or generated by code)                |

## 2. Doors and gates

One door system, many kinds, all data in `data/game.json` (`structures.types`) so a new door is a JSON entry plus a model.

| Kind                       | Behaviour                                                                           | Look and sound                         | Notes                                                               |
| -------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------- |
| Swing door (built)         | Open / closed; open it blocks nobody                                                | Hinge swing 90 degrees, creak          | Animate the rotation instead of sinking it (today it sinks)         |
| Double door, saloon        | Two leaves; a saloon door is never closed, it only slows                            | Two swings                             | Slows movement while pushed                                         |
| Sliding door               | Slides into the wall; opens when an ally is near (auto), closed otherwise           | Fast slide, motor hum                  | `auto: true` with a trigger radius                                  |
| Sci-fi iris / hexagonal    | Opens in 0.6 s from the centre; stays open while someone is in the doorway          | Segmented leaves, pneumatic hiss       | Needs a mesh per leaf, or a shader that dilates a hole              |
| Half-Life blast door       | Heavy, slow (3 s), needs a switch or power; warning light and siren while moving    | Massive slide, alarm, rumble           | `powered: true`, a switch entity, blocks line of sight while moving |
| Alien-style airlock        | Two doors in sequence; only one open at a time; pressure change of 4 s between them | Hiss, status panel, red / green lights | A pair with a shared state machine; a trap for hordes               |
| Keycard / terminal door    | Locked until a keycard item, a code, a hacking minigame or a story event            | Red / green panel                      | `locked` with a `key` item id from `items.json`                     |
| Large gate (base, vehicle) | Wide (6 to 10 m), two leaves or one sliding, vehicles drive through; slow           | Chain / motor, clang                   | Footprint over several 1 m cells; a break cost much higher          |
| Garage / shutter door      | Rolls up; open it clears the full width                                             | Rattling roll                          | Height animation only                                               |
| Breakable / jammed         | Hit points; a jammed door needs a crowbar or time; zombies can smash it             | Splinters, dents, sparks               | Already: closed doors have health and zombies attack them           |

Shared rules to decide (recommendations in the last column):

| Question                                  | Options                                                    | Recommendation                                                         |
| ----------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| When does a door open?                    | Press **E**; auto for allies; powered / remote; by event   | All four, as flags: `interact`, `auto`, `powered`, `script`            |
| Who can pass it?                          | Allies, soldiers, vehicles, specific enemies               | A `passes` list of unit families; enemies attack what they cannot pass |
| Does it block sight when closed / moving? | Yes / no per kind (glass doors do not)                     | A `seeThrough` flag; sight and movement are separate masks             |
| How long is "opening"?                    | Instant (today) or an animation that blocks while it moves | `openTime`: blocks until fully open; closing crushes nothing           |
| Locks                                     | None, key item, code, power, story                         | `lock` object: `{kind, key?, code?}`; the editor sets it per door      |

Test prop for all of this: **Map 7, Door gallery**: a corridor with one of each door in a row, a switch panel, a keycard crate, a powered door and an airlock pair, and a few zombies behind them. Nothing else, so each door can be played and tuned in a minute.

## 3. Interiors

An interior is a set of rooms: walls with gaps, doors, windows, floors, roofs, props. The sim only needs boxes and doors; most of the work is how it looks and how it plays.

| Topic             | Proposal                                                                                                                                                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Walls             | The same box obstacle as a prop, drawn thin (0.2 to 0.3 m) with a height of 2.6 m; a building is a list of wall boxes plus door slots, created from a **prefab** (a small JSON: footprint, walls, doors, windows, props)                             |
| Windows           | A wall segment with `seeThrough` and `passShots`: blocks walkers, not sight or bullets; breakable glass later                                                                                                                                        |
| Roofs             | A roof mesh per building that fades out when a unit is inside (the cutaway used by RTS and survival games); never part of the sim                                                                                                                    |
| Floors and stairs | **One floor first.** Upper floors need `y` layers in the sim: each obstacle and door gets a `floor` number, units have a floor, stairs are a link between floors; flow field and sight per floor. Large change, do it after one-floor interiors work |
| Lighting          | Dark interiors with the existing flashlight mode, plus point lights by prefab (lamps); more than a few real lights is costly, so bake or fake the rest                                                                                               |
| Editor            | A building tool: draw a rectangle, split it into rooms with clicks, drop a door where a wall is clicked, pick a prefab. Undo / redo and the Assets tab already exist                                                                                 |
| Gameplay hooks    | Close quarters make melee and shotguns matter; hiding in rooms for the stealth labs; defending a room with doors and a turret (build mode inside buildings)                                                                                          |
| Test prop         | **Map 8, Interiors lab**: a house (4 rooms, 2 doors, 3 windows), a warehouse (one large room with shelves as cover) and a bunker (airlock, corridor, locked door)                                                                                    |

## 4. Urban maps

| Topic                | Proposal                                                                                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Layout               | A grid of blocks separated by streets (8 to 12 m wide, painted with the road surface), buildings placed from prefabs along the sides, alleys between them, a plaza                           |
| Streets              | Roads already exist as a painted surface; add kerbs and sidewalks (a second surface), lamp posts, parked cars and barriers as props, wrecks as vehicles that can be driven                   |
| Generation           | Hand-made first (a 100 x 100 map with 4 blocks), then a seeded generator in the editor: choose size and density, it places prefabs; always editable afterwards                               |
| Streets and gameplay | Long sight lines (snipers, hunters, orb beams), choke points (alleys), cars as cover and as barricades, a horde that funnels along streets (the flow field already does this)                |
| Size                 | 100 x 100 m is 10,000 cells; the flow field search and the grid already handle that. A real city (500 m) needs chunked fields and building LOD: treat that as the engine phase               |
| Props                | Doors, windows, fences, bins, cars, lamps, benches, crates: one shared kit. Look for CC0 packs (Quaternius, Kenney) or build them from boxes and a few materials; list them in `assets.toml` |
| Test prop            | **Map 9, Urban block**: four blocks, a plaza, two streets, three enterable buildings, a parked-car row, a bus wreck blocking a street. This is also the town for Celestial Event 4           |

## 6. Soldiers in tight places

Soldiers move in straight lines and slide along boxes. Streets and rooms will trap them. Before interiors, give soldiers the zombies' flow field: a field per target, or a short A* on the same 1 m grid, used by `move`, `board`, `build` and `follow` orders. Doors that are closed count as passable for allies (they open them) and as a cost for enemies.

## 8. An engine for several games

The user's long-term idea: make a game engine to build several games on and keep experimenting. This repository is already most of one: a pure, deterministic 2D simulation (`src/sim`), a render layer that only reads state (`src/render`), a data-driven rules file validated by zod, a map format with an editor, a fixed-step loop, and now a systems list with orders, structures, doors and AI behaviours. What is missing is a **boundary** between "the engine" and "this game".

| Layer           | Belongs to the engine                                                                       | Belongs to the zombie game                                      |
| --------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Simulation core | Fixed step, seeded RNG, vectors, collision, grid, flow field, line of sight, orders, events | Waves, perks, shop, loot, bosses, downed state, the squad rules |
| Entities        | Units with teams, health, inventory, weapons, vehicles, structures, doors, triggers         | The roster (marine variants, zombies), the item catalogue       |
| Data            | The zod pipeline (schema + JSON + a strict error on typos), the map format, the editor      | `game.json` numbers, `items.json`, `characters.json`            |
| Render          | Scene, cameras (top, third, first person), lighting, character views, effects, health bars  | Materials and looks of this game, HUD, menus                    |
| Tools           | Editor, bench scripts, asset checker (license policy), credits generator                    | Content                                                         |

Proposed path (small steps, the game keeps working after each):

| #   | Step                                                                                                                                                             | Why                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| E0  | Draw the boundary in a doc: list `src/sim` files as engine or game, find the imports that cross it                                                               | Free, and shows how tangled it is                                                       |
| E1  | A **systems registry**: `step()` runs a list of systems (`updateSoldiers`, `updateStructures`, ...) from an array a game can extend or replace                   | The step is a hard-coded list today; the registry is the first real engine seam         |
| E2  | A **rules module** per game: the game registers its systems, its schema sections and its HUD; the engine only knows generic sections (units, teams, map)         | Lets a second game bring its own `game.json` sections                                   |
| E3  | Move the engine to `packages/engine` and the zombie game to `games/zombies` (npm workspaces); ESLint keeps `sim` free of Three.js and the DOM                    | Makes the boundary physical; lint already enforces the purity rule                      |
| E4  | A **second game** as proof: the hide-and-seek / stealth lab as its own small game, or a base-defence game on build mode                                          | An engine is only real when two games use it; the labs are already close to small games |
| E5  | Merge with Phase B ([PLAN-webgpu-engine.md](PLAN-webgpu-engine.md)): the render snapshot boundary and the worker sim are the same seam seen from the render side | One migration, not two                                                                  |

Risks and rules:

| Risk                                          | Mitigation                                                                                                         |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Over-engineering before a second game exists  | Do E0 and E1 only; E2 onwards when the second game starts. Extract from working code, never design in the abstract |
| Breaking the live game                        | Each step is a refactor with the 48 tests green and the dev server checked by the user                             |
| Licences when assets are shared between games | The asset check and `assets.toml` move with the engine; each game lists its own                                    |
| Naming                                        | The engine needs its own name later (the repo already mentions "Wylan Engine" in the credits): ask the user        |
